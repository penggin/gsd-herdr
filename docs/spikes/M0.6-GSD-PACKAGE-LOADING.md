# M0.6 — GSD-Pi Package and Runtime Resource Loading

> **Status:** Complete  
> **Date:** 2026-08-29  
> **Baseline:** `open-gsd/gsd-pi` `v1.16.2`  
> **Exact upstream commit:** `dda097fc89ce10b67e78faa0b947c22bb9ec96a2`  
> **Question:** Can a released GSD-Pi installation be safely modified by overlaying only `src/resources`?

## 1. Result

**No. A `src/resources`-only overlay is not a safe or effective patch mechanism for a normal released GSD-Pi installation.**

The released CLI starts from `dist/loader.js`. Its resource resolver prefers a complete `dist/resources` tree over `src/resources`, and the publish pipeline builds that tree before publishing. The selected resources are then synchronized into the managed agent directory, normally `~/.gsd/agent`, and extensions are loaded from the synchronized copies.

The effective production path is therefore:

```text
published @opengsd/gsd-pi package
└── dist/loader.js
    └── resolveBundledResourcesDirFromPackageRoot(packageRoot)
        ├── complete dist/resources exists → select dist/resources
        └── otherwise                    → fall back to src/resources
            
selected resources/extensions
    └── initResources()
        └── sync to ~/.gsd/agent/extensions
            └── DefaultResourceLoader / child --extension paths
                └── active bundled subagent implementation
```

A viable resource-overlay strategy must instead update or regenerate the **built `dist/resources` output**, update its managed-resource fingerprint, and cause the target agent directory to resynchronize. The final choice between a prebuilt resource overlay and a complete source build remains an M0.8 decision.

## 3. Evidence

### 3.1 The installed executable is compiled `dist/loader.js`

The root package declares:

```json
{
  "bin": {
    "gsd": "dist/loader.js",
    "gsd-cli": "dist/loader.js"
  }
}
```

The published file allowlist includes both `dist` and `src/resources`.

This means the presence of `src/resources` in the npm package does **not** imply that it is the active resource source. Runtime selection still determines which tree is used.

### 3.2 Runtime explicitly prefers `dist/resources`

`resolveBundledResourcesDirFromPackageRoot()` constructs both candidates:

```text
<packageRoot>/dist/resources
<packageRoot>/src/resources
```

It selects `dist/resources` whenever that directory contains both `agents` and `extensions`. Only an incomplete built tree causes fallback to `src/resources`.

This is deliberate. The resource loader comments describe `dist/resources` as the stable, build-time state and `src/resources` as the live working tree used when no complete build output exists.

Consequences:

- changing `src/resources/extensions/subagent/index.ts` in an installed release normally has no runtime effect;
- forcing the resolver to use `src/resources` by deleting or damaging `dist/resources` would violate the release's normal runtime assumptions and is not an acceptable installation strategy;
- the patch target for a released package is the built resource tree, not source resources alone.

### 3.3 `dist/resources` is compiled, not merely copied

The release build runs `scripts/copy-resources.cjs`. That script:

1. removes the previous `dist/resources` tree;
2. invokes TypeScript with `tsconfig.resources.json`;
3. compiles extension and shared TypeScript into `dist/resources`;
4. copies non-TypeScript files;
5. writes `.managed-resources-content-hash`.

`tsconfig.resources.json` maps:

```text
rootDir: src/resources
outDir:  dist/resources
```

and includes bundled extension and shared TypeScript while excluding tests.

Therefore a source patch must be compiled before it can become a correct production resource overlay.

### 3.4 The npm publish workflow builds before publishing

The npm workflow runs the core build before `validate-pack` and `npm publish`. The core build includes TypeScript compilation and `copy-resources`.

`validate-pack.js` then creates an npm tarball, checks required compiled files, installs the tarball into an isolated directory, and runs the installed binary. This provides strong release-pipeline evidence that a normal npm installation contains a usable built `dist` tree.

The repository tag does not need to track generated `dist/resources` files for them to exist in the npm release because they are produced during publication.

### 3.5 Bundled resources are synchronized into `~/.gsd/agent`

The loader discovers extension entrypoints under the selected bundled resource directory, but maps them to their eventual paths under the GSD agent directory. `initResources()` then synchronizes:

```text
<selected resources>/extensions → ~/.gsd/agent/extensions
<selected resources>/shared     → ~/.gsd/agent/shared
<selected resources>/agents     → ~/.gsd/agent/agents
<selected resources>/skills     → ~/.gsd/agent/skills
```

For print/subagent execution, `src/cli.ts` calls `initResources()` before constructing and reloading `DefaultResourceLoader`.

GSD subagent launches also propagate `GSD_BUNDLED_EXTENSION_PATHS`, whose entries point at the synchronized agent-directory copies. Thus the effective implementation executed by a child is normally the managed copy originating from `dist/resources`.

### 3.6 Editing `~/.gsd/agent/extensions/subagent` directly is not durable

The agent-directory extension is managed by GSD-Pi. A matching version and content fingerprint lets steady-state startup skip a full recursive resync, so a local edit may appear to survive temporarily. However, it is overwritten when a resource refresh occurs, including after:

- a package version change;
- a bundled-resource content-hash change;
- a forced or repaired resource synchronization;
- reinstall/update workflows that replace managed resources.

Directly modifying the synchronized copy is therefore unsuitable for a reproducible stack. It has no exact upstream provenance, no safe update semantics, and no reliable rollback boundary.

### 3.7 The precomputed resource fingerprint must be updated

`dist/resources/.managed-resources-content-hash` is trusted when it contains a valid fingerprint. `initResources()` compares that value with `~/.gsd/agent/managed-resources.json` and returns early when both package version and content hash match.

If an overlay changes `dist/resources/extensions/subagent/index.js` but leaves the precomputed fingerprint unchanged, an existing installation may continue loading the old synchronized file because GSD sees no resource change.

A correct built overlay must therefore:

1. modify the intended built resource files;
2. regenerate or deliberately remove the precomputed resource fingerprint;
3. ensure the target agent directory performs one controlled resync;
4. verify the synchronized file's digest after startup;
5. never rely on manually editing the managed copy.

Regenerating the fingerprint is preferable to deleting it in a released stack because it preserves deterministic content identity.

### 3.8 The bare published package is not a self-contained resource compiler

The root package publishes `dist` and `src/resources`, but its file allowlist does not include the repository-level `tsconfig.resources.json` or `scripts/copy-resources.cjs` build utility.

Therefore an installer should not assume that it can take a globally installed npm package, edit its TypeScript source, and invoke the upstream resource build in place.

Targeted resource compilation must instead happen in one of these controlled environments:

- an exact upstream source checkout with its build configuration and dependencies;
- `gsd-herdr` release CI, which produces an immutable overlay for an exact GSD-Pi version;
- a full patched source build.

## 4. Evaluated delivery options

### Option A — Patch `src/resources` in the installed npm package

```text
installed npm package
└── edit src/resources/extensions/subagent/index.ts
```

**Result:** Rejected.

Reasons:

- normal runtime selects complete `dist/resources` first;
- the source change is not compiled into the active tree;
- the installed package does not guarantee the upstream resource-build tooling needed to compile it;
- the approach encourages in-place mutation and poor rollback behavior.

### Option B — Patch the synchronized agent copy

```text
~/.gsd/agent/extensions/subagent/index.js
```

**Result:** Rejected.

Reasons:

- it is managed output, not an installation source;
- future resync can overwrite it;
- it bypasses exact package fingerprints and provenance;
- multiple GSD installations can contend for the same managed agent tree;
- rollback and compatibility checks become ambiguous.

### Option C — Overlay prebuilt `dist/resources`

```text
exact official npm package
+ exact-version prebuilt dist/resources overlay
+ regenerated managed-resource fingerprint
+ controlled agent-directory resync
```

**Result:** Technically viable; carry forward to M0.8.

Required conditions:

- overlay is generated from the exact upstream tag/commit;
- source patch compiles with the upstream resource compiler;
- output contains only the intended built-resource changes;
- `.managed-resources-content-hash` is regenerated;
- installation is side-by-side rather than mutating the active package;
- activation uses an integration-owned wrapper/path;
- smoke tests prove that the managed agent copy came from the overlay;
- local-vs-external subagent result parity still passes.

Advantages:

- potentially avoids rebuilding unrelated GSD packages and the web application;
- keeps the integration patch limited to the bundled extension surface;
- can be distributed as a small exact-version artifact.

Risks:

- generated JS and source patch must remain traceably paired;
- resource-only compilation may still depend on workspace packages and upstream build setup;
- a future GSD release may move the external-backend seam outside `src/resources`;
- wrapper and resource-manifest identity must not confuse GSD's version-mismatch gate.

### Option D — Full patched source build

```text
exact upstream source
+ generic seam patch
+ upstream build pipeline
→ side-by-side patched GSD distribution
```

**Result:** Technically robust; carry forward to M0.8 as fallback/reference implementation.

Advantages:

- follows upstream's intended build pipeline;
- tests can run against source and generated output together;
- fewer assumptions about which compiled artifacts are sufficient.

Costs:

- heavier CI and release artifact production;
- longer build time;
- more workspace/package outputs to stage and verify;
- greater maintenance burden than a proven resource overlay.

## 5. Provisional recommendation for M0.8

M0.8 should compare **Option C** and **Option D** empirically.

Preferred hypothesis:

```text
Build the generic seam from an exact GSD-Pi source tag in CI,
produce a prebuilt dist/resources overlay,
apply it to an isolated copy of the official npm package,
regenerate the fingerprint,
and activate it side-by-side.
```

Fallback:

```text
If resource-only output cannot pass the full subagent parity and packaging tests,
use a complete patched source build.
```

This is not yet the final distribution decision. M0.8 must prove that the resource-only overlay:

- is loadable from an installed-package layout;
- causes deterministic managed-resource resynchronization;
- preserves all runtime imports;
- supports the exact test surface required by the external backend seam;
- can be installed and rolled back atomically.

## 6. Required M0.8 experiment

Create an isolated temporary prefix and agent root, then perform:

```text
1. Obtain @opengsd/gsd-pi@1.16.2 and verify its package integrity.
2. Confirm dist/resources/agents and dist/resources/extensions exist.
3. Record hashes for:
   - dist/resources/extensions/subagent/index.js
   - dist/resources/.managed-resources-content-hash
4. Start the unmodified package once against an isolated GSD agent directory.
5. Confirm the synchronized subagent path and digest.
6. Generate a resource overlay from the exact v1.16.2 source.
7. Apply the overlay to a separate package copy.
8. Regenerate the content fingerprint.
9. Start the patched copy against the same isolated agent directory.
10. Confirm that one controlled resync installs the patched digest.
11. Run focused subagent tests and a fake external-backend smoke test.
12. Restore the original package pointer and prove rollback.
```

Do not perform this experiment against the user's active global GSD installation.

## 7. Constraints added to the project

The following constraints are now evidence-backed:

1. `src/resources` alone is not the production overlay target.
2. The active resource source is normally `dist/resources`.
3. The managed agent copy is output, not a patch target.
4. A built overlay must regenerate the managed-resource content fingerprint.
5. Existing managed resources must be resynchronized deterministically.
6. Patch generation must use an exact upstream source identity.
7. Installation remains side-by-side; active package mutation is prohibited.
8. Final selection between a resource overlay and full source build is deferred to M0.8.

## 8. Confidence and remaining uncertainty

**Confidence in the runtime-path conclusion: high.** It is directly supported by the tagged loader, resolver, resource synchronizer, tests, package manifest, and publication workflow.

This session could not perform a local `npm pack`/tarball extraction because the execution environment could not resolve external package hosts. The source and release-pipeline evidence is sufficient to reject a `src/resources`-only overlay, but the exact mechanics and size of a distributable built overlay still require the isolated M0.8 experiment.

## 9. M0.6 completion statement

M0.6 is complete with the following verdict:

> A released GSD-Pi installation cannot be safely modified by overlaying only `src/resources`. The normal runtime selects compiled `dist/resources`, synchronizes it into the managed GSD agent directory, and may skip synchronization based on a precomputed content fingerprint. Any supported overlay must use exact-version built resource output, regenerate the fingerprint, and trigger a controlled resync; otherwise the project must distribute a complete patched build.
